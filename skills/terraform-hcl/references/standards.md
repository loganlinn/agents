# Terraform/HCL Standards

Source basis:

- Cloud Posse Terraform Best Practices: https://docs.cloudposse.com/best-practices/terraform/
- AWS IA Terraform standards: https://aws-ia.github.io/standards-terraform/

Use this as a compact decision guide. Prefer explicit local repo policy when it exists; otherwise apply the stricter compatible rule.

## Quick Checklist

Reusable child modules:

- Module has a focused purpose and is not a thin wrapper around provider resources.
- Child modules declare `required_providers` and version constraints but do not configure provider blocks.
- Provider aliases use `configuration_aliases`; callers pass concrete provider configs with the `providers` meta-argument.
- Variables have snake_case names, descriptions, explicit types, positive boolean names, safe defaults, validations where useful, and `sensitive = true` for secrets.
- Complex related inputs are modeled as one object or map/object rather than many loosely related variables.
- Dynamic resources use `for_each` with stable keys. Use `count` only for 0-or-1 conditional creation.
- Outputs are named clearly, described, composable, and free of secrets.
- Repo includes working examples, tests, generated docs, and conventional Terraform file names.

Root modules and environments:

- Root modules configure provider authentication, regions, profiles, assume-role chains, `default_tags`, backends, and environment-specific behavior.
- State uses a remote backend with locking, encryption, versioning, and local state files ignored by Git and Docker build contexts.
- S3 state buckets require encryption, versioning, strict IAM access, and should not be provisioned by the same state they store.
- External module sources are pinned exactly. Git module refs must point to immutable tags or commits, not branches.

Repo hygiene:

- Terraform is formatted, validated, linted, tested, and docs are regenerated when interfaces change.
- Do not commit plans, state files, crash logs, provider caches, credentials, or generated local backend config containing secrets.
- Ignore local state artifacts and exclude Terraform state artifacts from Docker build contexts.

## Module Structure

Prefer this layout for reusable modules:

```text
main.tf
variables.tf
outputs.tf
versions.tf
examples/<name>/
modules/<submodule>/      # only when decomposition is real
test/ or tests/
README.md                # generated or partly generated by terraform-docs
```

Use service-named files only when a coherent group, such as IAM roles and policies, is large enough that keeping it in `main.tf` reduces clarity. Every reusable module should have at least one working example. Name the simplest example `basic` when there is no better repo convention.

Tests should exercise examples and important module behavior. Terratest is common in AWS IA-style repos; `terraform test` may be appropriate where the repo already uses it.

## Provider Boundaries

In reusable child modules:

- Declare provider sources, constraints, and aliases in `required_providers`.
- Do not configure credentials, profile, assume-role chains, regions, or `default_tags`.
- Do not add backend blocks; Terraform ignores child-module backend configuration.
- Use aliased providers only when the module genuinely needs multiple provider instances.
- Document expected caller wiring when aliases are required.

Preferred child-module alias declaration:

```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = ">= 5.0"
      configuration_aliases = [
        aws.source,
        aws.target,
      ]
    }
  }
}
```

Preferred root-module caller wiring:

```hcl
module "replication" {
  source = "./modules/replication"

  providers = {
    aws.source = aws.us_east_1
    aws.target = aws.us_west_2
  }
}
```

## Variables

Use upstream provider or module argument names when they are clear and already familiar. Otherwise use lower snake_case.

Prefer:

```hcl
variable "create_dashboard" {
  description = "Whether to create the CloudWatch dashboard."
  type        = bool
  default     = true
  nullable    = false
}
```

Avoid negative booleans such as `disable_dashboard`; they create double negatives in conditions and examples.

Use `nullable = false` when `null` is not a meaningful user choice. Use no default for required secrets and mark them sensitive:

```hcl
variable "api_token" {
  description = "API token used by the integration."
  type        = string
  sensitive   = true
}
```

For optional features, prefer one of these patterns:

- Boolean feature flag for simple create-or-not behavior.
- Empty map/list default for many optional child resources.
- Object with optional attributes for related configuration.

Prefer one cohesive object for related settings when the settings are usually understood together:

```hcl
variable "alarm" {
  description = "CloudWatch alarm configuration."
  type = object({
    enabled             = optional(bool, true)
    evaluation_periods  = optional(number, 3)
    threshold           = number
    notification_topics = optional(list(string), [])
  })
}
```

Add validation blocks for non-obvious constraints, enum-like values, region/service keys, CIDR bounds, and mutually constrained values. Keep validation errors actionable.

## Outputs

Every output should have a description. Use lower snake_case. Prefer symmetrical names between inputs, resources, and outputs when that helps consumers predict the interface.

Output values that downstream modules compose with: IDs, ARNs, names, endpoint URLs, resource objects when appropriate, and normalized tag maps. Never output secrets.

When wrapping a primary resource, consider outputting the whole resource object in addition to common scalar fields if that reduces future interface churn without exposing secrets.

## HCL Style

Run `terraform fmt -recursive`.

Use contextual resource names:

```hcl
data "aws_region" "current" {}

resource "aws_route53recoveryreadiness_cell" "per_region" {
  for_each = toset(var.regions)
}
```

Avoid generic names such as `this`, `self`, or `bucket` unless the surrounding repo consistently uses them and the resource role is unambiguous.

Prefer resource prefix arguments, such as `name_prefix` or `bucket_prefix`, when random suffixes reduce naming collisions and the provider supports them. Use Terraform functions for network math instead of hand-coded CIDR strings. Use locals to name opaque or repeated expressions.

Use indented heredocs for long human-readable text. Do not use heredocs for JSON, YAML, or IAM policies; use `jsonencode`, `yamlencode`, or provider data sources such as `aws_iam_policy_document`.

## Dynamic Resources

Prefer `for_each` over `count` because stable map/set keys avoid index churn in state. Use `count` only for simple zero-or-one resource creation.

When starting from a list of unique strings, `toset(var.names)` is acceptable. For objects, build a map keyed by a stable logical identifier:

```hcl
for_each = {
  for subnet in var.subnets : subnet.name => subnet
}
```

Do not key `for_each` by values likely to change during normal edits unless replacement is intended.

## Tags And Names

All taggable resources should accept and apply tags. Let root modules decide provider default tags.

Pick the naming/tagging helper that matches the ecosystem:

- Cloud Posse-style modules: use `terraform-null-label` for consistent names and labels.
- AWS IA-style modules: use `terraform-aws-label` when normalizing AWS and AWSCC tag shapes.

If a repo already has a naming abstraction, extend it rather than introducing a competing one.

## State And Backends

Root modules should configure backend settings. Reusable child modules should not contain backend blocks.

Use remote state with locking. For S3-backed state, require encryption, bucket versioning, and strict IAM access. State buckets should be provisioned with Terraform, but not by the same state they store.

Ignore local Terraform artifacts:

```gitignore
.terraform
.terraform.tfstate.lock.info
*.tfstate
*.tfstate.backup
```

Exclude Terraform state artifacts from Docker build contexts, commonly with `**/.terraform*`.

## Module Sources And Versioning

Use Terraform Registry source syntax with exact versions when possible:

```hcl
module "label" {
  source  = "cloudposse/label/null"
  version = "0.25.0"
}
```

For Git sources, pin to immutable tags or commits. Avoid branch refs. Prefer explicit tag refs when the ecosystem expects them.

For public modules, use semantic versioning after the first stable release. Treat breaking input/output behavior, resource addressing changes, and state migration requirements as breaking changes.

## Documentation And PR Checks

Regenerate README tables with `terraform-docs` when variables, outputs, providers, or examples change. Keep hand-written usage guidance above or around generated sections according to repo convention.

Run the repo's pre-commit hooks or equivalent CI commands. Common checks include:

- `terraform fmt -recursive`
- `terraform validate`
- `tflint`
- security scanning such as tfsec or Checkov
- tests for examples
- generated docs drift

If ignoring a lint or security finding, add a precise code comment or PR note explaining why the exception is intentional and what bounds the risk.

## Conflict Resolution

When Cloud Posse and AWS IA conventions differ:

- Follow the repo's owning ecosystem first.
- Do not introduce both `terraform-null-label` and `terraform-aws-label` in the same module without a clear compatibility reason.
- Keep Cloud Posse's stricter exact module pinning rule for module calls.
- Keep AWS IA's provider-boundary rule for reusable child modules.
- Prefer the smaller interface that preserves composability.
